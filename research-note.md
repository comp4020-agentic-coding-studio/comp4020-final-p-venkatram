# Research note

## Agentic development should go broad before it goes deep — and the agile consensus against this doesn't transfer

Agile practice has spent three decades converging on a single answer to "what do you build first": a thin, end-to-end vertical slice. Alistair Cockburn's walking skeleton is the clearest statement of it — "just enough of a solution to demonstrate a small end-to-end functionality for a single vertical slice of the system," deliberately *not* disposable, because the alternative — building out one architectural layer at a time before anything connects — is named directly as an anti-pattern and a root cause of tech debt. The reasoning suits the problem it was built for: when a team of people each hold an incomplete, slightly different mental model of the system, integration failures hide until the layers finally meet, and by then they are expensive. A thin slice through every layer surfaces that risk on day one, while still giving parallel human work shared seams to coordinate around.

I want to argue that this prescription, correct as it is for human teams, does not transfer to agentic software development. The walking skeleton solves a *coordination* problem — multiple people, multiple incomplete models, surprises at the seams between them. A single agent generating a codebase has a different failure mode: drift. Nothing stops a capable model from making a locally reasonable but globally inconsistent decision in one corner of a large generation task, since nothing it generated ten minutes ago pins down what it generates now, except whatever context survives. The risk is not "the layers don't meet," it's "the thing has no single coherent shape by the time it's all written" — which calls for fixing the broad shape first, not a thin slice through it.

That is the rationale now showing up in 2026's spec-driven development literature, independently of agile orthodoxy. Tools like GitHub's spec-kit and AWS Kiro fix architecture, constraints, and acceptance criteria *before* any agent writes code, so the spec becomes what one practitioner calls a "consistency anchor": for a system with many interconnected components, it stops the agent making inconsistent decisions across different parts as it fills in detail. This isn't deciding every detail upfront, which would just be Big Design Up Front under a new name, and agile's objection to BDUF (decisions locked in before any feedback exists) still applies — it's the shape that needs fixing early, with detail improvised against it afterward rather than dumped in all at once.

Detailing one slice first also carries a cost the walking skeleton doesn't account for: that slice's specific choices become a template the rest of the system gets measured against, even where other parts need a different level or kind of detail. Broad-first avoids this, since detail stays local to wherever it's being filled in rather than exported from whichever slice got built first.

Broad-first also inverts the walking skeleton's own justification for itself. Part of Cockburn's case for vertical slices is parallel work: a thin end-to-end slice gives a human team shared integration points to coordinate around. But once a broad skeleton exists — architecture and interfaces fixed, detail not yet filled in — the natural unit of parallel work becomes "fill in this blank," module by module, which is exactly the shape 2026 multi-agent frameworks already take: separate agents for investigate, plan, implement, and verify around one shared spec. That divides agentic labor at least as well as a vertical slice divides human labor, without needing the slice at all.

The same shift shows up in the prompt itself. If the architecture already pins down consistency, a prompt doesn't need to carry as much of that burden in prose — consistent with 2026's rise of deliberately terse, telegraphic prompting tools like the viral "Caveman Protocol," which strips filler from agent instructions and which JetBrains' own benchmark found caused no detectable drop in task success or code quality. Once the broad shape carries the consistency, the marginal prompt doesn't need to re-specify it.

There is empirical support underneath this too. Jiang et al.'s self-planning code generation work shows LLMs that decompose and plan before generating code outperform direct generation by up to 25.4% (Pass@1). Agent-scaffolding research treats this as settled enough to build into tooling directly: frameworks like PaperCoder and AutoP2C place a dedicated architecture-and-roadmap planning stage before any code generation and call it the most critical stage in the pipeline, since it's where the consistency of everything downstream gets decided.

None of this means the walking skeleton's underlying concern — discovering your architecture is wrong only once everything is built — stops mattering for agents. The fix just looks different: validate the broad shape cheaply (a spec review, a small executable check, an end-to-end smoke test the agent runs itself) before committing to detail, rather than building one thin path through every layer. Vertical-slice-first is a specific answer to a human-shaped coordination problem, not a timeless law of software engineering — and a solo generative process doesn't share that problem.

The field is already moving here in practice, through spec-first tooling and planner subagents, faster than it is saying so out loud. It should say so: agentic development has its own canonical build order, running in the opposite direction from the one agile spent thirty years teaching people to use.
